### Technical Highlights
- **2m 9.4s end-to-end is the headline metric.** That's the wall clock from the fixed-camera trigger to a verified incident with three robots successfully dispatched, two video-reasoning rounds completed, TTS broadcast, and the Q5 at the first-aid location with the kit. ~9 LLM calls (5–13 s each), 26 tool calls (most sub-3-second, two video-reasoning calls at 4–8 s each), all parallelised where the dependencies allowed.
- **Parallel tool calls are the dominant throughput lever in practice.** Every turn where Claude could batch, it did. Turn 1: `update_incident` + `list_schema_aliases` + 3× `get_action_schema` (all in parallel). Turn 2: `update_incident` + 3× `send_action` to dispatch Go2/X2/Q5 simultaneously. Turn 3: 3× `add_incident_action` + `update_incident_status`. Turn 4: 3× `monitor_action_execution`. If those had been sequential, the demo would run 6–8 minutes instead of 2.
- **Vendor-agnostic schema is the foundation everything else stands on.** The agent issued `send_action(device_id=GO2, action="navigate_to_pose", payload=...)`, `send_action(device_id=X2, action="navigate_to_pose"...)`, `send_action(device_id=Q5, action="motion_replay"...)` through the *same* function signature. Three different vendors (Unitree, Agibot, RobotEra), three different on-robot SDKs (Unitree SDK, AIMDK, XOS), three different locomotion API models (continuous odom, streaming velocity with arbitration, FSM-gated TwistStamped), one Praxis action schema. The integration work from weeks 3–5 validated under multi-robot orchestration.
- **Staged confidence escalation tells the audit story.** 50% at camera detection → 75% after Go2's visual reasoning → 95% after X2's casualty check. The trace records *which sensor* contributed *which evidence* to *which confidence boost*. Leadership asked "how do we know the system is right?" — the staged trace is the answer. Each tier is a different robot's evidence; the system is right because the evidence is independently sourced.
- **Local Gemma path stays viable as the air-gapped fallback.** Demo ran on Bedrock Claude for the live runtime (parallel tool calls, ~2 min). The same agent, same prompt, same tool set is wired to vLLM-hosted Gemma-26B too — runs slower (~6–8 min, no parallel calls) but works without an internet dependency. For the Impact event the safety of an air-gapped fallback matters more than the headline number.
- **Recipe-style prompt held under live conditions.** Every behaviour the prompt forces — fixed robot roles (no swaps), same-location dispatch (X2 to incident not demo hall), mandatory post-`video_reasoning` chain (always escalates confidence in the same turn as the visual), narration discipline (two narrations total: Go2 arrival + casualty check) — landed correctly across the live demo. Zero prompt regressions during the Boss demo run.

### Academic Connections
- **AI agents / orchestration.** Multi-agent task allocation under fixed-role constraints — the planning literature calls this "role-constrained team coordination." Each robot has a fixed capability domain (scout / announcer / intervener); the agent's job is sequencing, not allocation. The constraint reduces the planning problem from NP-hard team assignment to a deterministic playbook.
- **Bayesian decision theory.** Staged-verification confidence (50 → 75 → 95%) as a literal Bayesian update with multi-sensor evidence. Each robot's `video_reasoning` produces a likelihood; the agent composes likelihoods into a posterior. The transparency of the trace makes the prior, the likelihood, and the posterior all auditable — a property real Bayesian systems rarely expose.
- **Distributed systems.** Parallel tool calls as a literal implementation of fork-join concurrency at the agent layer. Same shape as pipelined RPC, same throughput win (3× in this trace), same correctness obligation: independent calls must be truly independent for parallelism to be safe. The prompt enforces this by listing exactly which calls can batch.
- **Vendor abstraction / interface design.** Three vendors, three protocols, one schema — same architectural pattern as POSIX, JDBC, ODBC, gRPC. The win is the same: applications written against the interface don't change when the implementation changes. The Praxis SDK is "POSIX for robots" within the fleet we've integrated.
- **Robotics / behaviour design.** Multi-tier verification with role-specialised sensors is the algorithmic frame for human-safety-critical robotic intervention. The pattern generalises: tier 1 = fastest sensor (camera), tier 2 = mobile observer (Go2), tier 3 = human-proximity-rated platform (X2), action tier = physical intervention (Q5). Each tier earns higher confidence at the cost of higher latency; the choice of stopping tier is a risk/latency trade-off.
- **Human-factors.** The demo's pacing — 2 minutes from trigger to resolution, with narration only at two high-information points — is engineered to be *observable by humans in real time*. A faster demo would be illegible; a slower demo wouldn't ship. Narration discipline + visible confidence escalation gives leadership a story they can repeat back. That's not a technical detail; it's why the demo got greenlit.
