## June 26, 2026

### Summary
Two-week arc closing out the Praxis multi-robot integration story. **Week 5 (Jun 15–21)** brought Agibot X2 Ultra and RobotEra Q5 to full Praxis fleet parity — completing the four-robot integration (alongside Go2 and A2) under a single platform schema across three architecturally-distinct locomotion API models (continuous odom, streaming velocity with arbitration, FSM-gated `TwistStamped`). **Week 6 (Jun 22–26)** built the agentic layer that sits on top of those drivers: self-hosted vLLM-served Gemma 26B for the local LLM, then `impact_agent` for the multi-robot incident-response playbook, then a live 2m 9.4s end-to-end Boss demo of the fallen-boxes scenario — greenlit for the Impact event.

### Technical Highlights
- **Three pose-estimation strategies under one schema, validated under multi-robot orchestration.** Week 5 added the X2's IMU-fused absolute-yaw + commanded-velocity pattern (no `/odom` topic, fused quaternion from chest IMU) and the Q5's odometry-delta integration with FSM-gated `TwistStamped`. With the Go2's vendor-fused odom and the A2's discrete-RPC-commit from prior weeks, the fleet now has four architecturally-distinct robots under the same Praxis `set_pose` / `navigate_to_pose` schema. The Fri demo proved this isn't theoretical: the agent issues `send_action(device_id, "navigate_to_pose", payload)` identically across Go2, X2, and Q5 — three vendors, three SDKs (Unitree SDK / AIMDK / XOS), three locomotion API models, one platform-level interface.
- **Multi-source arbitration on X2 is a control-plane primitive separate from the data plane.** Publishing to `/aima/mc/locomotion/velocity` succeeds at the DDS layer but the AIMDK arbiter discards messages from unregistered publishers. The driver registers via `SetMcInputSource` at startup with explicit high priority; commands take effect within one control cycle thereafter. Classifies the third "publishes but doesn't move" root cause across the fleet alongside Q5's FSM-not-ACTIVE and the host's DDS-implementation-mismatch.
- **Settle-by-sensor-feedback beats RPC-return trust.** Q5's XOS motion-replay HTTP endpoint returns ~immediately on accept; naïve sequencing made the chassis walk while arms were mid-gesture. The settle detector watches `/joint_states` for motion start (any body joint velocity > 0.1 rad/s) and motion end (max(|velocity|) < 0.05 rad/s continuously for 1 s), with an empirically-derived exclusion list (wheels + left wrist + left hand for residual encoder noise). The pattern is reusable for any robot with HTTP-triggered fire-and-forget motion libraries.
- **Self-hosted vLLM is the platform inversion.** The agentic layer's central LLM dependency moves from hosted Bedrock to a workstation Blackwell GPU. Fixed amortized cost (zero marginal per token), byte-stable model behaviour (pinned `vllm-openai:v0.21.0` image, pinned weights via HF cache), data residency (prompts and completions never leave the host). PagedAttention + continuous batching make the GPU work hard enough that a 26B model competes with hosted Claude on wall-clock for our bursty agentic workload. OpenAI-compatible HTTP API means LiteLLM swaps providers with a single string change.
- **Recipe-style prompts beat abstraction for *any* model size.** Same prompt, written abstractly, was unreliable even on Claude. Rewriting as a literal recipe — fixed role table, literal payload JSON, "in the SAME TURN as `video_reasoning`, call X then Y then Z", bad-vs-good narration examples — turned a 70%-reliable behaviour into a 100%-reliable one. *Prompt specificity inversely correlates with required model capability.* A 4B-active model with a 200-line recipe outperforms a 4B-active model with a 30-line abstraction. The behavioural-cloning-via-prompt insight is the methodological contribution of the week.
- **Staged-verification confidence (50 → 75 → 95%) as the algorithmic story.** Each tier is a different robot's evidence; the trace records *which sensor* contributed *which evidence* to *which confidence boost*. Generic template for any future incident type — tier 1 = source signal, tier 2 = first-tier robot confirms visual, tier 3 = second-tier robot rules out human harm. The audit story leadership can repeat back: "how do we know the system is right? Three independent sensors each contributed evidence."
- **Parallel tool calls are the wall-clock lever for agentic workloads.** Demo trace shows Claude batching 3 `get_action_schema` then 3 `send_action` then 3 `monitor_action_execution` in single turns. 26 tool calls in ~2 min; serialised, ~6–8 min. The throughput win is identical to pipelined RPC: 3× wall-clock improvement for batch-able work. Gemma 4 can't batch (model-capability ceiling); Claude can. Engineering response: Bedrock Claude for the live runtime, local Gemma as the air-gapped fallback.
- **Provider-agnostic LiteLLM + vendor-agnostic Praxis SDK = composable abstractions.** Two abstractions stacking: vendor-neutral robots (Praxis SDK) × vendor-neutral models (LiteLLM) = workflow-neutral incident responses (the `impact_agent` playbook). Model switch is a config-line change; robot switch is a `device_id` change in the payload. The agent code is invariant across both axes.

### Impact
- **Praxis multi-robot incident-response demo greenlit for the Impact event.** The complete pitch: warehouse incident → camera detection → agent dispatches three robots through identical schemas → audited confidence escalation → casualties verified absent → first aid positioned, all in 2m 9.4s natural-language-commanded.
- **Four-robot fleet integration complete.** Unitree Go2 (quadruped), Agibot A2 Ultra (life-sized humanoid), Agibot X2 Ultra (bipedal humanoid), RobotEra Q5 (wheeled humanoid). Same Praxis API, same SDK contracts, same action vocabulary, same on-robot service substrate patterns. The schema-uniformity-with-implementation-flexibility design hypothesis is now an empirical claim.
- **Production-grade staged-verification template.** 50 → 75 → 95% confidence with sensor-source attribution is reusable for fire, intrusion, equipment failure, medical emergency. Slots into the same recipe-style prompt with different `video_reasoning` prompts and role assignments.
- **Cost trajectory de-risked.** Demo runs against Bedrock Claude (~$0.05/run) and against locally-served Gemma-26B (zero marginal cost). Repeated rehearsals during Impact event week have no billing exposure. Predictability matters more than absolute savings.
- **vLLM runbook + failure-modes documentation** are institutional memory for every Blackwell-host bring-up that follows. CUDA Error 803, "no kernel image", OOM, 401, port collisions — all in a fixed-shape table mapping symptom to cause to fix.
- **Recipe-style prompt is a transferable artefact.** Any team building an LLM-driven robotic workflow can lift the shape: fixed role assignment, literal payload JSON, "in this exact order", mandatory post-action update chains, narration discipline, fixed-template final report. The behavioural-cloning-via-prompt pattern is reusable beyond the incident-response context.
- **Diagnostic playbook for "publishes but doesn't move" complete across the fleet.** Four root causes now documented: DDS implementation mismatch (FastDDS host vs CycloneDDS robot, Q5), FSM not in ACTIVE state (Q5), multi-source arbiter not registered (X2), QoS profile mismatch (A2). Check in that order; one will be it.

### Academic Connections
- **Robotics theory.** Three SE(2) dead-reckoning strategies (vendor odom / discrete RPC / IMU-fused) under one schema; differential-drive vs holonomic path decomposition; chassis-class-parameterised navigation behind a uniform action surface; velocity ramping as discrete-time acceleration limit.
- **Distributed systems.** Multi-source publisher arbitration as control-plane primitive separate from topic data plane; DDS implementation interoperability gaps (CycloneDDS vs FastDDS); HTTP fire-and-forget vs RPC task-id polling vs sensor-feedback settle as three implementations of the same long-running-operation pattern; OpenAI-compatible REST as vendor-neutral interface contract.
- **Operating systems / virtual memory.** PagedAttention as direct application of OS-style paging to KV cache (page tables, lazy block allocation, copy-on-write); continuous batching as token-level preemption analogous to tick-driven scheduler preemption.
- **Systems / linker semantics.** `LD_LIBRARY_PATH` resolution order and library shadowing as the root cause of CUDA Error 803 on Blackwell hosts — a class of dynamic-linker bug that looks like a hardware problem.
- **AI agents / orchestration.** Recipe-style prompts as behavioural-cloning at the prompt layer; same-turn vs sequential tool-call enforcement; parallel tool calls as agent-layer fork-join concurrency; staged-verification confidence as multi-sensor Bayesian update with auditable evidence attribution; provider-agnostic LiteLLM as model-layer vendor abstraction; their composition with Praxis SDK as workflow-neutral substrate.
- **Decision theory.** Staged-verification confidence (50 → 75 → 95%) as literal Bayesian update with multi-sensor, multi-vendor likelihood composition; the auditability of prior + likelihood + posterior is a property real Bayesian systems rarely expose.
- **Control theory.** Vendor-exposed finite state machines over service interfaces (Q5's `INIT → IDLE → READY → ACTIVE`); driver-orchestrated FSM transitions vs operator-owned preflight; graceful-degradation as a partial-failure policy.
- **Sensor fusion / signal processing.** Vendor-fused quaternion vs raw gyro+accel integration trade-off; commanded-velocity-as-reference vs IMU-acceleration-as-feedback for position; continuous-below-threshold over a settle window as a debounce filter; multi-channel `max(|velocity|)` aggregation with rationale-documented exclusion lists.
- **Software architecture.** Schema-uniformity-with-implementation-flexibility at the platform/driver boundary AND at the agent/model boundary; chassis-class-parameterised behaviour under a uniform action API; image-pinning + bind-mounted state + pre-flight verification as a hygiene pattern; failure-modes taxonomy as forcing-function documentation; hot-reload via volume mount as iteration-loop optimisation.
