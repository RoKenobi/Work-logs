# Daily

## June 29, 2026

**Graph Nodes:** [[Praxis Platform]], [[Praxis SDK]] · #Python #OpenCV #FFmpeg #Docker #RTSP #H264 #MQTT #HTTP #VendorAbstraction

**Theme:** [[Robotics Integration Infrastructure]]

### Summary
Shipped `praxis_hk_vision` — the first **non-robot** driver on the Praxis platform. Wraps a wall-mounted Hikvision IP camera (`192.168.123.100`) as a Praxis device with the same observability surface as a robot (online card, floor-plan pin, live RTSP video), while honestly modelling the physical reality that a CCTV has no joints, no battery, no commandable motion. Plain-Python driver (no ROS 2) in two Docker Compose services with host networking, ~600 LOC. Validates the SDK's vendor-abstraction design beyond moving hardware.

### Shipped
- **`praxis_hk_vision` driver package** under `praxis_drivers/`. Three console-script entry points (`hk_vision_video_streamer`, `hk_vision_camera_info_publisher`, `hk_vision_camera_status_publisher`). Plain `setup.py` + `pip install -e .` — no `colcon`, no `rclpy`, no tmuxinator. The first deliberately non-ROS-2 driver in the fleet.
- **RTSP video streamer** — joins `rtsp://admin:***@192.168.123.100:554/Streaming/channels/102` (Hikvision sub-stream, 640×360 @ 6 fps); pipes frames through `praxis_client.create_video_streamer(...).stream_frame(frame)` which transcodes via FFmpeg-subprocess libx264 and pushes to Praxis RTSP at `rtsp://192.168.123.150:8554/{device-id}/front`. Outer reconnect loop wraps the inner OpenCV read loop; tolerates camera reboots, network blips, and Praxis backend restarts without operator intervention. Steady-state stats every 10 s at INFO (`Streaming: 4875 frames, actual FPS: 6.0, retry_count: 0`).
- **Camera status publisher** with three responsibilities reconciled into one 0.5 Hz heartbeat: (1) custom `camera_status` JSON on `<org>/<location>/<device>/states/camera_status/<camera_name>` (QoS 1, `retain=true`); (2) mirror into the canonical `robot_status` topic via `RobotStatusPublisher` so the device card flips from "Offline" to "Online"; (3) re-publish `robot_pose` on the **floor_plan** frame every 2 s so the floor-plan viewer renders the camera pin.
- **Mount-pose env-driven config** — `HK_VISION_MOUNT_{X,Y,Z}` and `HK_VISION_MOUNT_YAW` (operator-friendly degrees) in `docker-compose.yml`, overridable from `.env`. Yaw → quaternion conversion at publish time. `validate_map_id=False` on the publish call because `floor_plan_id` is not in `client.robot_map_ids` (those are robot-map UUIDs, a distinct namespace).
- **Two-service Compose stack** sharing one image (`praxis-hk-vision:latest`). `video-streamer` has the `build:` block; `camera-status` references the already-built image to avoid the BuildKit "image already exists" race when both services build in parallel. `network_mode: host` sidesteps Docker NAT for RTSP/MQTT on the same physical LAN. SDK + driver bind-mounted from host so `docker compose restart <service>` after a `.py` edit picks up the change without rebuild. `restart: unless-stopped` + `sudo systemctl enable docker` = unattended-restart on both process and host failure.
- **`set_pose` action handler removed** — earlier iteration registered it (with JSON-on-disk persistence under `./state:/data`) so the dashboard's "Set Robot Pose" button could relocate the camera at runtime. Per deployment feedback, the handler is gone. The "Set Robot Pose" button now correctly fails. A wall-mounted CCTV's location is a physical deploy property; the only legitimate source of truth is `docker-compose.yml`.

### Technical Highlights
- **Plain Python over ROS 2 — vendor abstraction extends to *non-robot* devices.** The other drivers inherit ROS 2 because they wrap moving hardware whose telemetry is high-rate and multidimensional. A CCTV's surface area is one RTSP URL + one fixed pose. Wrapping that in `rclpy.Node` / `MultiThreadedExecutor` / parameter declarations / tmuxinator profiles adds ceremony without buying anything — no joints, no odom, no `cmd_vel`, no `tf` tree, no need for `colcon`. The Praxis SDK speaks MQTT/HTTP directly; that's the right abstraction for stationary sensors. The fleet now has two driver shapes — *ROS 2 ament_python* for robots, *plain Python* for sensors — under the same SDK contract.
- **OpenCV + FFmpeg over GStreamer.** Hikvision's RTSP is RFC-compliant H.264 over RTP, which OpenCV's FFmpeg backend handles out of the box. Two knobs do the work: `OPENCV_FFMPEG_CAPTURE_OPTIONS=rtsp_transport;tcp` (forces TCP, trades a small latency cost for stability — UDP loses packets on busy LANs producing visible artifacts) and `CAP_PROP_BUFFERSIZE=1` (OpenCV's default buffer queues several frames; setting 1 keeps the pipeline near-live). No `gst-plugins-bad/ugly` to wrestle with.
- **The floor-plan viewer's three implicit contracts.** Initial pose-publish used `PosePublisher(client, topic_name="camera_pose_front")` with `frame.type="robot_map"`. Dashboard never rendered. Traced to `praxis_robots/api/static/js/floor_plan_viewer.js`: it subscribes specifically to `*/+/+/states/pose/robot_pose` (topic name must be `robot_pose`, not custom), filters by `frame.type === 'floor_plan'` (not `robot_map` — those are distinct namespace identifiers in the platform; `PRAXIS_MAP_ID` is a robot-map UUID, the dashboard wants the floor-plan UUID from `?id=...`), and applies a 10-second max-age filter (`max_age=10`, so a one-shot publish on startup vanishes). Fix: default topic name, `floor_plan` frame type with the floor-plan UUID, republish every 2 s on the heartbeat. Three contracts, all undocumented except in the JS source.
- **`battery_level=100.0` for a mains-powered camera.** A wall-powered device is trivially always "fully charged." Pinning the field rather than omitting it avoids the device card's "no battery data" placeholder and matches the shape `robot_status` expects downstream consumers to receive. Cheaper than special-casing the schema.
- **Why mirror `camera_status` → `robot_status`.** Two topics, same heartbeat tick. `camera_status` carries the camera-specific fields (`vendor`, `rtsp_path`, `width`, `height`, `fps`, error fields). `robot_status` satisfies the canonical dashboard device-card consumer (which doesn't know about cameras). Mapping `online → idle` because "idle" is the `robot_status` enum value the card displays as a healthy green. Adapter pattern at the schema layer.
- **Clean-shutdown contract.** On `SIGTERM` the publisher emits a final `camera_status` with `status="offline"` so downstream consumers can distinguish "process crashed (last-known retained message still saying online)" from "process stopped cleanly (offline received)." Symmetric to the systemd-managed substrate pattern from earlier weeks.
- **BuildKit race in dual-service Compose.** Both services need the same image; both build it in parallel by default; result: one wins, the other fails with "image already exists" mid-tag. Fix: only one service has `build:`, the second references `image:` only and uses `depends_on:` to sequence startup. Sounds obvious in hindsight; cost an hour to diagnose.

### Impact
- **First sensor on Praxis.** The platform's device card, floor-plan viewer, RTSP stream consumer, and MQTT bus all treat the CCTV as just another device. From the cloud-side `concierge_agent`'s point of view, the camera is a `device_id` with a fixed pose and an RTSP path — same schema shape as a robot, different on-device implementation. Extends the vendor-agnostic-action-schema design from robots to stationary sensors with zero platform changes.
- **Sub-second end-to-end video latency** on LAN, ~6 fps at 640×360. `ffplay rtsp://192.168.123.150:8554/<device-id>/front` plays live within sub-second of the source. Device card flips from "Offline" to "Online" within ~2 s of `camera-status` startup. Floor-plan renders the camera at `(6.797, -0.168)` with the sensor-style marker (green dot + R/G axes) rather than the robot-style pill — correct because the device is registered with `type: sensor`.
- **The deliberate-removal of `set_pose` is itself a design statement.** Earlier iterations let an operator click "Set Robot Pose" to relocate the camera on the map at runtime, with JSON-on-disk persistence under `./state:/data`. Removed per deployment feedback: a wall-mounted camera's location is a deploy property, not a runtime property. The button's error dialog is now the correct behaviour. Source of truth lives in exactly one place: `docker-compose.yml`. Eliminates two failure modes (accidental click during multi-device view; ambiguous source of truth between `.env`, persisted JSON, and last-dashboard-click).
- **600 LOC, one image, two compose services, zero ROS 2 dependencies.** Smallest driver in the fleet by an order of magnitude. Day-N operations limited to `docker compose logs -f <service>` / `docker compose restart <service>`. The minimalism is the contribution — it sets the floor for what a "Praxis device" can be.

### Academic Connections
- **Software architecture.** Vendor abstraction at the platform layer that extends from moving robots to stationary sensors — same SDK contract, different physical-device shapes. Adapter pattern at the schema layer (mapping CCTV's natural status enum to `robot_status`'s expected vocabulary). Source-of-truth discipline: removing runtime mutability for properties that should be deploy-time-only.
- **Distributed systems.** MQTT retained-message semantics for last-known-good device state; QoS 1 + retain combining at-least-once delivery with snapshot recovery; final-message-on-shutdown as a graceful-vs-crash distinguisher; topic-name as an implicit interface contract (the dashboard's `robot_pose` subscription is the schema; deviating breaks rendering with no error).
- **Computer vision / media.** RTSP-over-TCP vs UDP trade-off (latency cost for packet-loss stability); OpenCV `VideoCapture` buffer semantics (`CAP_PROP_BUFFERSIZE=1` for near-live); FFmpeg subprocess re-encode as the unifying media-pipeline substrate across the fleet (Go2 / X2 / Q5 / HK Vision all converge on `libx264 → MediaMTX RTSP`).
- **Operating systems / packaging.** Host-mode Docker networking for LAN-local services that need direct multicast or unprivileged port binding; build-context discipline (`.dockerignore` at the right level keeps the context under 1 MB); bind-mount-driven hot reload as the iteration loop for interpreted languages in containers.
- **Concurrency.** Outer-reconnect / inner-read loop pattern with bounded backoff as the canonical streaming-source resilience shape; thread-per-source (capture in a daemon thread, MQTT in the main thread) as a minimal concurrency model when the producer and consumer are decoupled by the SDK's queue.
