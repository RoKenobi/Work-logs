### Summary
Resolved the two remaining blockers to A2 production readiness: the AIMDK-vs-Praxis map-id namespace mismatch that caused every `SpinTurnAndMoveForward` to fail with `CommonState_FAIL`, and the FastDDS profile + `ROS_DOMAIN_ID` + `ROS_LOCALHOST_ONLY` interaction that prevented the in-process publishers from discovering AIMDK topics. A2 now runs end-to-end on a single `praxis_start` alias with a six-line `pre_window` sourcing chain that no operator has to remember.

### Shipped
- **AIMDK map-id pinning in the executor** — driver now carries both `PRAXIS_MAP_ID` (UUID) and the internal AIMDK 64-bit map-id (`1780391953779`) and sends the latter in `SpinTurnAndMoveForward` payloads
- **Deployment runbook entry** — explicit note that the AIMDK map-id must be re-aligned whenever the on-board SLAM map is rebuilt; the two namespaces are independent and must be kept in sync manually
- **`profiles/praxis_agibot_a2_ultra.yml`** — production tmuxinator session with the canonical six-line `pre_window`:
  1. `source /opt/ros/humble/setup.bash`
  2. `export ROS_DOMAIN_ID=232`
  3. `export ROS_LOCALHOST_ONLY=0`
  4. `export FASTRTPS_DEFAULT_PROFILES_FILE=/agibot/software/v0/entry/bin/cfg/ros_dds_configuration.xml`
  5. `source /agibot/agibot_a2_aimdk-dev2.0/prebuilt/ros2_plugin_proto_aarch64/share/ros2_plugin_proto/local_setup.bash`
  6. `source /agibot/a2_ws/install/setup.bash` then `source /agibot/praxis_ws/install/setup.bash`

### Technical Highlights
- **Two map-ids, two namespaces.** The AIMDK PNC service rejected every navigation request with `CommonState_FAIL` because the payload's `map_id` was being filled with the Praxis UUID (`96835da7-…`). PNC expects the AIMDK map-id — a 64-bit integer generated by the on-board mapping pipeline. The two are wholly independent namespaces; nothing in the schema indicates this. Fix is mechanical (pin both IDs in the driver), but the diagnosis required tracing a `CommonState_FAIL` back through the AIMDK runtime logs to the SLAM map UUID mismatch.
- **FastDDS profile + domain-id + localhost-only is a three-variable footgun.** The driver could see AIMDK topics from a directly-spawned `ros2 topic list`, but the in-process publishers never discovered them. Root cause: `FASTRTPS_DEFAULT_PROFILES_FILE` was unset (or pointed at the default profile, which restricts discovery to localhost). The vendor's `ros_dds_configuration.xml` opens loopback *and* sets a multicast TTL appropriate for the on-board network. The tmux profile now pins all three: domain-id, profile path, and explicit `ROS_LOCALHOST_ONLY=0` to defeat a stray `=1` in someone's `.bashrc`.
- **Source-line order is significant, not cosmetic.** ROS core → domain+locality → FastDDS profile → vendor proto-msg bridge → vendor AIMDK workspace → Praxis driver. Reordering breaks `aimdk_msgs` / `a2_services_pkg` / `ros2_plugin_proto` imports because each overlay depends on the previous one being present in `AMENT_PREFIX_PATH`. Encoding the order into `pre_window` is the only way to make this reproducible across operators.
- **Discovery diagnosed via inside-process vs outside-process asymmetry.** The clue that pointed at FastDDS profile (not topic name, not message type, not QoS) was that `ros2 topic list` from a separate shell saw the topics while the driver process did not. Same machine, same network — the only variable was environment inheritance. That's a useful diagnostic heuristic: when discovery is asymmetric across process boundaries on the same host, suspect FastDDS profile / `ROS_LOCALHOST_ONLY` first.

### Impact
- A2 driver reaches READY status against the `@assess-integration` agent. Full Praxis fleet parity: BMS, arm joint state, pose (discrete-dead-reckoned), and video stream live; `set_pose`, `navigate_to_pose`, and `motion_replay` actions flow back; the systemd substrate handles AIMDK restart cycles transparently.
- Operator bring-up reduced to one alias on top of the systemd substrate — `praxis_start` brings up the entire driver stack in a tmux session with the correct environment, no human-remembered source lines.
- Map-id mismatch is now an explicit runbook step; the next person re-mapping the on-board SLAM will know to update the driver constant rather than discovering the failure through `CommonState_FAIL` retries.
- The asymmetric-discovery heuristic ("if `ros2 topic list` sees it but my process doesn't, suspect FastDDS profile") is now in the team's debugging playbook.

### Academic Connections
- **Distributed systems.** Namespace separation across federated identity systems (vendor SLAM map UUID vs platform map UUID); the cost of conflating namespaces at API boundaries. Multicast group discovery semantics (TTL, locality scope). Environment-driven configuration as a runtime contract.
- **Networking.** Multicast TTL and locality scope as a determinant of DDS discovery; the difference between "interface up" and "discovery reachable"; `ROS_LOCALHOST_ONLY` as a coarse-grained discovery filter.
- **Software architecture.** Configuration-as-environment-variable pattern; idempotent `.bashrc` mutation with atomic backups; layered workspace overlays (ROS core → vendor messages → vendor SDK → application driver); fail-fast environment validation at process boundaries.
- **Systems programming.** Overlay ordering in `AMENT_PREFIX_PATH`; `colcon` symlink-install for hot Python reload; `tmuxinator` as a process-tree templating system for environment-sensitive workloads.
